## Investigation Summary: VoiceOver Duplicate Reading Issue
I've identified the source of the VoiceOver duplicate reading issue when using Option+Left/Right Arrow in VS Code. Here's my analysis:
### Root Cause Analysis
The duplicate reading occurs due to conflicting announcement systems when crossing punctuation boundaries during word navigation:
1. VoiceOver's native text reading - macOS VoiceOver naturally reads text as cursor moves
2. VS Code's accessibility signal system - Makes explicit announcements via ARIA live regions
3. VS Code's screen reader content system - Updates hidden textarea content for screen readers
### Key Problem Areas
1. Word Boundary Detection (`src/vs/editor/common/core/wordHelper.ts:10`)
- Colon `:` is classified as `USUAL_WORD_SEPARATORS`
- When cursor moves `foo → : → number`, each transition triggers separate word boundary events
2. Explicit Cursor Announcements (`src/vs/editor/contrib/wordOperations/browser/wordOperations.ts:59`)
- Word navigation commands use `CursorChangeReason.Explicit`
- This triggers accessibility signals that make announcements via `accessibilityService.status()`
3. Dual Announcement Systems (`src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts:127`)
- VS Code makes announcements through ARIA live regions
- VoiceOver also reads the updated screen reader content naturally
- Both systems announce the same content change
4. ARIA Live Region Conflicts (`src/vs/base/browser/ui/aria/aria.ts:53-59`)
- VS Code uses alternating containers to prevent duplicate message filtering
- However, this may interfere with VoiceOver's natural reading flow
### Specific Fix Recommendations
1. Immediate Fix - Disable Accessibility Signals for VoiceOver
In `src/vs/workbench/contrib/accessibilitySignals/browser/editorTextPropertySignalsContribution.ts:88-95`:
```typescript
// Skip accessibility signals for VoiceOver on macOS during word navigation
if (this.isVoiceOverActive() && e.reason === CursorChangeReason.Explicit) {
    return; // Let VoiceOver handle announcements naturally
}
```
2. Detection Method
Add VoiceOver detection in `src/vs/platform/accessibility/browser/accessibilityService.ts`:
```typescript
private isVoiceOverActive(): boolean {
    return this.isMacOS() && this.isScreenReaderOptimized();
}
```
3. Alternative Approach - Timing Coordination
Extend the existing `setIgnoreSelectionChangeTime()` mechanism in `src/vs/editor/browser/controller/editContext/native/screenReaderSupport.ts:49-58` to coordinate with VoiceOver's natural reading timing.
### Files Most Likely Responsible
1. `src/vs/workbench/contrib/accessibilitySignals/browser/editorTextPropertySignalsContribution.ts` - Primary source of duplicate announcements
2. `src/vs/editor/browser/controller/editContext/native/screenReaderSupport.ts` - Screen reader content management
3. `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts` - ARIA live region announcements
4. `src/vs/base/browser/ui/aria/aria.ts` - ARIA live region implementation
### Why Other Editors Don't Have This Issue
TextEdit and Xcode don't implement custom accessibility signal systems - they rely entirely on the native macOS accessibility APIs that VoiceOver expects, avoiding the conflict between multiple announcement systems.
The fix requires detecting VoiceOver specifically and disabling VS Code's redundant accessibility announcements during word navigation, allowing VoiceOver to handle text reading naturally without interference.
